# Veriforge Product & Technical Bible v1.0

## 1. Product identity

**Veriforge** is my living evidence system for the systems I build, the decisions I make, the failures I learn from, and the proof I collect.

It is not a normal portfolio, resume, GitHub wrapper, or LinkedIn replacement. It is a proof engine.

## 2. Core tagline

> Where my work becomes proof.

## 3. Core positioning

I do not just list projects. I map my claims to evidence: case files, decisions, failures, tests, architecture, demos, and shipped work.

Veriforge exists to answer one question better than a resume can:

> Why should someone trust me to build, test, debug, and ship serious systems?

## 4. Narrative

I started from QA, but I do not want to stay boxed into checking screens. I use QA thinking to build safer systems: systems that control automation, expose failures, validate decisions, and turn vague ideas into testable products.

My story connects:

```text
QA -> debugging -> automation -> AI safety -> approval systems -> product building
```

## 5. Product principles

### Evidence first

If I cannot prove it, I do not claim it.

### First-person ownership

Veriforge speaks in my voice:

- I designed...
- I built...
- I tested...
- I learned...
- I would improve...

It must not sound like a third-person profile written about me.

### Honest maturity

Every project is labeled by proof maturity. Ideas are ideas. Prototypes are prototypes. Tested systems are tested systems. Nothing gets inflated.

### Future-proof system

Everything I build in the future can enter Veriforge, but only after it earns proof.

### No-bullshit rule

If I cannot prove it, I do not claim it.
If it is only an idea, I label it as an idea.
If it is not tested, I do not call it production-ready.
If it failed, I document the failure and the fix.
If I used AI, I explain how I directed, reviewed, tested, or validated the work.

## 6. Primary audience

### Technical interviewer

They need to inspect my architecture, debugging ability, testing strategy, tradeoff thinking, and proof.

### Recruiter or hiring manager

They need to understand role fit quickly without digging through every repo.

### Founder or collaborator

They need to see whether I can turn messy ideas into scoped, useful, buildable systems.

## 7. Main modules

### Mission Control

The landing page. It should explain Veriforge in ten seconds and route visitors into proof.

Core actions:

- Inspect Proof Claims
- Enter Case Files
- View Proof Wall
- Open Interview Mode
- Ask Veriforge
- Generate Evidence Pack

### My Narrative

A concise first-person explanation of how I moved from QA into automation, AI safety, approval systems, debugging, and product building.

### Proof Claims

A claim is a capability statement backed by evidence.

Example claims:

- I design control systems for risky automation.
- I debug complex automation systems by separating symptoms from root causes.
- I turn vague ideas into structured, testable, buildable systems.
- I use QA thinking to design safer product workflows.
- I create human-in-the-loop systems where automation needs control.

Every claim must link to proof.

### Case Files

A case file is a structured investigation of a project.

Each case file includes:

- Case ID
- Project name
- Status
- Proof maturity
- Signal score
- Core claim
- Problem
- Why it matters
- My role
- System design
- Key decisions
- Failure log
- Testing strategy
- Proof
- Demo readiness
- Proof gaps
- Before / After
- Interview talking points
- What I would improve next

### Proof Wall

A dashboard of evidence items across projects.

Evidence types:

- PR
- Test
- Architecture doc
- Product bible
- Demo
- Failure fix
- Decision log
- CI/CD proof
- Security control
- User/workflow proof

### Failure Ledger

A public record of meaningful failures and what I learned.

Format:

- Failure
- Bad assumption
- Root cause
- Fix
- Test added or needed
- What it proves

### Decision Ledger

A record of important product and technical decisions.

Format:

- Decision
- Context
- Options considered
- Chosen path
- Rejected path
- Reason
- Tradeoff

### Build Log

A raw progress log showing what changed over time.

Format:

- Date
- Project
- What I worked on
- What changed
- What broke
- What I learned
- Proof link

### Before / After

A section that shows transformation.

Example:

Before: I wanted to approve AI-agent work from my phone.
After: I shaped it into Aixion Control Tower: approval lifecycle, backend API, Android approval flow, GitHub worker, payload hash, and MCP gateway wait mode.

### Operating Style

How I work:

- I turn vague ideas into scoped systems.
- I prefer proof over claims.
- I treat failures as debugging material.
- I care about controls, tests, and real execution.
- I do not consider a project serious until it has proof.

### Interview Mode

A role-based guided proof path.

Modes:

- Recruiter Mode
- Technical Interviewer Mode
- QA Lead Mode
- AI Safety Mode
- Founder Mode
- Product Builder Mode

### Ask Veriforge

An evidence-grounded Q&A layer. It should answer from structured case files, proof items, decisions, failures, and build logs.

Answer format:

- Claim
- Evidence
- Example
- Limitation
- Suggested follow-up

Generic motivational answers are not allowed.

### Evidence Packs

Role-specific proof packs.

Pack types:

- QA Automation Evidence Pack
- AI Safety Evidence Pack
- Product Builder Evidence Pack
- Founder/Collaborator Evidence Pack
- General Recruiter Evidence Pack

## 10. Project intake rule

A future project enters Veriforge only when it has at least one serious proof artifact:

- clear problem statement
- scope document
- architecture
- prototype
- test evidence
- decision log
- failure log
- demo
- PR/code proof
- user feedback

## 11. Evidence ownership rule

Every case file must show what I personally did:

- What I designed
- What I implemented
- What I tested
- What I reviewed
- What AI/tools helped with
- What I personally validated

## 12. Proof gap rule

Every serious case file should include:

- Current proof
- Missing proof
- Next proof target

This prevents overclaiming and makes the next work obvious.

## 13. Signal score

Each project receives a signal score based on:

- Clarity
- Proof strength
- Technical depth
- Real-world usefulness
- Interview value
- Build maturity

The signal score is not ego. It is prioritization.

## 14. Visual direction

Use:

- dark graphite background
- off-white text
- amber or electric blue accent
- case-file cards
- evidence stamps
- maturity badges
- command-center panels
- minimal motion
- system diagrams

Avoid:

- cartoon UI
- overdone animations
- fake hacker terminal everywhere
- generic portfolio templates
- motivational quote sections
- random 3D effects

## 15. MVP success criteria

Veriforge MVP is successful if:

- a visitor understands my positioning in ten seconds
- a technical person can inspect proof in under two clicks
- each major claim has evidence
- each flagship case file has failure and decision sections
- the proof wall does not contain vague self-praise
- interview mode gives role-specific paths
- project maturity is visible and honest

## 16. MVP failure criteria

Veriforge fails if:

- it looks like a normal portfolio
- it has many projects but no proof
- it has animations but weak substance
- it makes claims without evidence
- it includes too many half-baked ideas
- it uses generic passionate-learner language

## 17. Final scope statement

Veriforge is a living proof engine that presents my builder journey through claim-to-proof traceability.

It organizes projects into case files, maps skills to evidence, exposes failures and decisions, supports interview-specific proof paths, and later adds AI-powered Q&A and evidence pack generation.

The first version focuses on three flagship systems: Aixion Control Tower, MCP Shield, and Tradebot.

The goal is not to look impressive. The goal is to make my capability inspectable, believable, and hard to dismiss.
